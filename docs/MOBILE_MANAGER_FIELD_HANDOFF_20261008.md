# OPERIS — мобильный контроль явки внутри существующих модулей

**Фиксация:** 08.10.2026. **Ветка:** `feature/mobile-manager-field-20261008`. **PR:** #89 (draft), зависит от PR #88 (личный кабинет сотрудника). **Production/staging БД не изменялись.**

## Последнее решение пользователя — обязательное

Менеджеру объекта нужен удобный **телефонный способ работать с существующим OPERIS**, а не вторая CRM, не отдельное приложение и не другой полнофункциональный desktop. На компьютере остаётся нынешний OPERIS. Мобильная явка должна выдерживать 30–100 человек на объекте, без больших карточек на каждого; быстрый ФИО/телефон/профессия/статус/смена, одна короткая строка, отметки «на месте / неявка». Первый выход — бейдж в строке и детали в контекстной панели. Выезд — мобильное представление существующего плана запуска и чек-листа. Никаких дублирующих сущностей, повторного ввода документов/СИЗ, удаления таблиц или перестройки меню.

## Обновление мобильного UX — одобрение исходного компактного реестра, затем телефонная итерация

После замечания пользователя «получилась упрощённая версия компьютера» интерфейс переработан в **phone-first представление существующего /shifts**, без отдельного приложения:
- Нет тяжёлой page-header, компьютерных вкладок и четырёх KPI-плиток на телефоне. Наверху название «Явка», объект, день/ночь, дата со стрелками и краткая строка состояния; показатели по статусам переключаются горизонтальными компактными фильтрами.
- Поиск открывается только по нажатию, профессия выбирается в нижней панели, массовый выбор включается отдельно. Сотрудники — короткие строки с ФИО, специальностью, индикатором состояния, звонком, одной кнопкой «На месте» и меню подробностей.
- Фиксация неявки требует отдельной панели с причиной, различаются «Ожидаем / уточняем» и окончательное подтверждение.
- Контекстная панель новичка показывает данные документов/СИЗ из той же карточки сотрудника без повторного ввода; контрольные отметки первого дня отдельно.
- Снизу **контекстные быстрые переходы** внутри раздела «Смены и выходы» — «Явка», «Запросы», «Выезды». Это не отдельная глобальная навигация и не другой информационный контур. Существующий OPERIS остаётся доступным через своё меню.
- На десктопе оставлены прежние модули и компоновка, включая полноценный планировщик.
- В отдельном автономном HTML-предпросмотре без БД проверены 60 тестовых людей в нескольких объектах, мобильные ширины 320/360/390/430 px, отсутствие горизонтального переполнения и ошибок JavaScript, поиск, фильтр профессии, массовый выбор, детали новичка, согласования, выезд, тёмная тема. **Это QA именно автономного макета, не реального staging.**

## Что фактически изменено

- `/shifts` и `GlobalShiftsWorkspace`: сохраняются две прежние вкладки «Контроль выходов» и «Графики и смены». На **desktop** остаются исходные `WorkerConfirmationManager` и `ResourceScheduler`. В мобильном «Контроле выходов» для ролей с `operations.shift.read`, `worker.read` и `operations.object.read` показывается `MobileShiftControls`; если не хватает разрешений, возвращается прежнее представление.
- `components/MobileShiftControls.tsx`: плотный телефонный список явки, строки около 56px, название/профессия/объект, цветовая точка, контакт, две короткие кнопки действий; дата, объект, день/ночь, поиск по ФИО/телефону/специальности/объекту, фильтр профессии и статуса («Не проверены», «Неявки», «На месте», «Первый выход»); неподтверждённые выше проверенных; режим выбора нескольких сотрудников одного объекта с явным подтверждением массовой явки.
- **Неявка**: «Нет на месте» открывает быстрый выбор результата проверки; «Ожидаем / уточняем» не превращает ожидание в окончательную неявку, «Подтвердить неявку» фиксирует факт; последующее прибытие формирует новое событие. Для звонка — `tel:` на фактический номер из карточки.
- Первый день — в общей строке «Первый выход», при нажатии на ФИО контекстная панель с уже известными из OPERIS сведениями по документам и СИЗ и ссылкой на карточку сотрудника; короткие реальные отметки менеджера: встретили, проверили пропуск, инструктаж, приступил. `worker_first_day_checkpoints` — отдельные аудируемые операционные контрольные пункты, а не альтернатива основной СБ/документам/СИЗ.
- Запросы сотрудников отображаются в компактной вкладке внутри существующего «Контроля выходов», действия используют исходный API `/api/operations/worker-confirmations`.
- В существующем `LaunchExecutionWorkspace` телефон при открытии выезда показывает прежде всего неуточнённые вопросы; компактные CSS-правила для исходного `launch-visit-drawer` с сохранением всех ответов и настроек на компьютере.
- `/field` остался как **совместимый перенаправляющий адрес** на `/shifts`; отдельное приложение/навигационный пункт «Рабочий день менеджера» и старый отдельный компонент удалены.
- `app/mobile-manager.css` — только scoped CSS для `/shifts` и мобильной страницы выездов; цвета и плотность из визуальных токенов OPERIS, обе темы.
- `lib/operations/mobile-manager.ts`, `/api/field-manager` — используем существующие `attendance_events`, `shift_assignments`, `worker_profiles`, `objects` и каноническую запись факта, с ограничениями tenant, actor, capability. Массовая отметка только по одному объекту и одной смене за транзакцию. **Никакого автоматического табеля/начисления часов по кнопке явки**. Сотрудник без назначения не может получить фиктивную явку.
- `migrations/0073_mobile_first_day_checkpoints.sql` — аддитивная схема для коротких контрольных событий первого выхода; RLS и аудит. **Не применялась к staging/prod.**
- `app/api/launches/[id]/visits/[visitId]/route.ts` допускает обновление одного вопроса `itemUpdate`, не стирая остальные ответы. Основная мобильная UX-форма использует существующий `LaunchExecutionWorkspace`.

## Проверки и известные риски

Последний полный CI проверять по актуальному HEAD PR #89: typecheck, lint, тесты, build и postgres-integration. Исторический успешный CI до новой компактной интеграции: https://github.com/avdeevgreyfog-cmd/outsourcing-operations-os/actions/runs/37779859405. Прототип можно открыть локально как автономный HTML из чата. **Автономный HTML имеет фиктивные данные и не подключается к БД**, не является доказательством реального E2E.

Обязательные staging-тесты: 30–100 сотрудников, день/ночь, фильтры/поиск/телефон, выбор одного/нескольких, объектные scope, причина/ожидание/неявка, повторное прибытие, audit, права manager/nonmanager, наём с первой даты, необходимость допуска, заранее проверенные документы/СИЗ, неавтоматическое начисление часов, мобильное согласование, редактирование существующего выезда и сохранение других вопросов, 320/360/390/430px, Safari/Android, светлая/тёмная тема, desktop регрессия. Ручной браузерный QA **реального Next-сайта** и живые E2E ещё не выполнены.

Особенность demo: в GitHub Pages статический API недоступен. Для демонстрации интерактивности используется **отдельный HTML с вымышленными данными**. Реальный мобильный экран требует API и аутентификации в staging.

## Строгие релизные ограничения

PR #89 направлен в ветку **PR #88**, потому что мобильная явка использует его workflow и миграции. **Не сливать в main или beta напрямую**. Сначала разобраться с production/staging DB boundary, отсутствующим `PRODUCTION_DATABASE_URL`, schema drift и release lineage; полный план зафиксирован в `docs/employee-portal-release-handoff-2026-10-08.md`. Без подтверждения отдельных баз не применять `0068–0073`, не промоутить изменения и не менять credentials.
