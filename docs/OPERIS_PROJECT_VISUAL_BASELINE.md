## Поправка 04.10.2026: согласованный стандарт перенесённых реестров

Эта поправка применяется к `/workers` и `/requests` и заменяет противоречащие ей
исторические размеры и схемы сентября ниже. Основа, бизнес-процессы, Golden Path,
модель прав и глобальная навигация не меняются. Другие модули и доски не считаются
автоматически перенесёнными.

| Элемент | Актуальное правило для перенесённого реестра |
|---|---|
| Заголовок таблицы / строка | 42 / 60 px |
| Основное название / вторичная строка | 13 px / 600 и 12 px |
| Кнопка / поле | 38 px, радиус 7 px |
| Таблица / смысловые панели | радиус 8 px / 8–10 px по роли |
| Статус | семантическая точка 6 px + русская подпись; без плашки |
| KPI заявок | в «Аналитике», без обязательного дубля над таблицей |
| Верхние виды заявок | «Таблица / Доска / Аналитика» и главные действия |
| Панель реестра заявок | слева поиск, этап и фильтры; справа вид, группы, колонки, сортировка и сохранение |
| Составная ячейка | максимум две строки; клиент, адрес и специальности доступны отдельными колонками |
| Колонка доски заявок | 228 px desktop; 210 px при ширине экрана до 600 px |
| Боковая панель сотрудника / коммерческий drawer | 560 / 490 px, максимум 100vw; ширина зависит от роли панели |
| Горизонтальная прокрутка | нативная плюс общий бегунок у нижнего края видимой рабочей области |

Геометрия вынесена в общие токены `app/registry-patterns.css`:
`--registry-row-height`, `--registry-header-height`, `--registry-control-height`,
`--registry-identity-size`, `--registry-secondary-size`.
Цвета перенесённых таблиц, настроек и боковых панелей наследуют текущую светлую или
тёмную тему из `app/globals.css`, включая `--panel`, `--panel-2`, `--text`, `--muted`,
`--soft`, `--border`, `--accent` и семантические токены. Светлая primary-кнопка сохраняет
контрастный `#C64C0B` с белым текстом; тёмная использует `--accent` с тёмным текстом.

Настройки колонок, группировки и нижний бегунок общие у сотрудников и заявок.
Сохранённый вид хранит порядок, ширину, закрепление, фильтры и сортировку, но не поиск.
Это предпочтения текущего браузера с существующим разделением по рабочему пространству
и правам; синхронизация между устройствами и подмена серверных данных не добавлены.
Массовые действия и пагинация сотрудников не становятся обязательными для всех реестров.

Аналитика использует компактные смысловые блоки, честные пустые состояния и «—» при
неизвестном знаменателе. Воронка с минимальной шириной этапа условная: её силуэт не
является точной шкалой количества. Демонстрационные записи и отсутствие истории
обозначаются явно. Никакие числа не создаются для заполнения графиков.

**Приоритет согласования:** последние явные решения пользователя → датированная
поправка к контракту → актуальный `docs/OPERIS_UI_STANDARD.md` → исторический baseline.
Код подтверждает состояние реализации, но не означает автоматического согласования
любого отличия. Для ещё не перенесённых модулей production / `main` остаются исходным
визуальным ориентиром. Preview и `beta` используются для проверки; их публикация не
является promotion в production. Проверки фиксируются по факту отдельно для каждого выпуска.

Визуальный каталог: `public/references/operis-ui-standard.html` (v1.3); автономные
примеры не отправляют и не сохраняют бизнес-данные. Подробный контракт и карта внедрения:
`docs/OPERIS_UI_STANDARD.md` и `docs/UI_SYSTEM.md`.

## Поправка 05.10.2026: согласованный стандарт реестра тендеров

Эта поправка распространяет визуально-реестровый контракт 04.10.2026 на `/tenders`.
Она не заменяет сохранённую ниже поправку 04.10 для `/workers` и `/requests` и не
объявляет остальные модули перенесёнными. Основа продукта, доменные workflows и
существующие подробные серверные формы тендеров сохраняются.

| Элемент | Актуальное правило для `/tenders` |
|---|---|
| Заголовок таблицы / строка | 42 / 60 px |
| Основное название / вторичная строка | 13 px / 600 и 12 px |
| Колонки | 20 доменных доступны настройкам; 8 в исходном основном виде |
| Общие controls | колонки, группировка и нижний бегунок используют общий реестровый паттерн |
| Сохранённый вид | раскладка и ширины, закрепление, группировки, фильтры, сортировка; без поиска |
| Группировка | максимум два уровня |
| Верхние виды | «Таблица / Доска / Аналитика»; KPI только в «Аналитике» |
| Доска тендеров | существующие 9 этапов; 228 px desktop / 210 px до 600 px |
| Коммерческий drawer | 490 px, максимум 100vw; нативный modal drawer |

Виды — локальные предпочтения браузера со scope существующих прав и рабочего
пространства; они не подменяют серверные записи. Перемещение по клавиатуре требует
эффективного права `sales.tender.edit` и права на конкретную строку; переход в этап
«Подано» дополнительно требует `sales.tender.submit`. Завершение проходит через
результатное действие на карточке с обязательным результатом, а не drag-and-drop.
Demo additions хранятся только в памяти и пропадают при перезагрузке; в аналитику
не включаются. API форм и схема БД не менялись, миграций нет.

Аналитика опирается на записанные события этапов. Когорта ограничена тендерами,
созданными в периоде; календарные события учитывают более ранние тендеры. Синтетическая
история не генерируется, непроверенный backfill исключён. Неизвестные бюджет и
численность дают знаменатель «—». При очистке последнего записанного результата старый
триггер не фиксировал событие; точные даты очисток не восстанавливаются и не
приписываются задним числом.

Проверочная ветка `ui/tenders-registry-standard` основана на `beta` SHA `6c5d8f1`.
`main` / production остаётся неизменным; Preview не означает promotion. В этой поправке
не фиксируется результат QA до отдельного отчёта по реально выполненным проверкам.
Каталог обновлён до v1.3 и содержит явно фиктивный пример тендеров.

# 4. Основная визуальная концепция

OPERIS — это **плотная профессиональная B2B операционная система**, рассчитанная на ежедневную работу менеджера в течение рабочего дня.

Это не:

- лендинг;
- маркетинговый SaaS;
- декоративный dashboard;
- AI-интерфейс;
- glassmorphism;
- bento-layout ради красоты;
- набор крупных карточек;
- яркая цветная CRM.

Основные принципы:

- светлый рабочий холст;
- спокойная серая иерархия;
- оранжевый только как основной action/accent;
- зелёный / жёлтый / красный / синий только семантически;
- высокая, но комфортная плотность;
- таблицы важнее карточек;
- borders before shadows;
- небольшие радиусы;
- понятная иерархия;
- минимум декоративных поверхностей;
- данные не удаляются ради «воздуха»;
- перегруз решается группировкой, вкладками, фильтрами и контекстными панелями.

# 9. KPI / summary metrics

Эталон: Заявки, Клиенты, КП, Тендеры.

Историческая схема сентября: **четыре небоксированных показателя**. Она не обязательна для каждого реестра; у перенесённых заявок KPI находятся в «Аналитике».

```css
grid-template-columns: repeat(4, minmax(0,1fr));
```

Между показателями:

- тонкие вертикальные разделители;
- снизу один общий divider;
- без общего жирного контейнера;
- без отдельных карточек.

### Значение KPI

```css
font-size: 28px;
font-weight: 650;
```

### Подписи

```css
font-size: 12px;
```

Если нет данных:

**`—`**

а не искусственный `0%`.

- horizontal overflow принадлежит таблице, а не всей странице;
- hover очень мягкий;
- статусы не должны превращать строку в цветную гирлянду.

---

# 15. Статусы

Цвет используется только семантически.

Примеры:

- green = положительный / завершённый;
- amber = предупреждение / внимание;
- red = ошибка / просрочка / проблема;
- blue = информационный этап;
- neutral = обычный текущий статус.

### Status baseline

Ниже — историческая плашка. В перенесённых реестрах действует точка 6 px с подписью, без background, padding и рамки статуса.

```css
font-size: 12px;
border-radius: 5px;
padding: 4px 8px;
```

Не использовать raw enum codes в UI.

Пользователь всегда видит человекочитаемый русский текст.

---

# 16. Доска / Kanban

Историческая базовая колонка сентября; доска заявок использует 228 / 210 px по поправке октября. Другие доски не меняются автоматически:

```css
width: 272px;
min-width: 272px;
border-radius: 10px;
```

Карточка:

```css
border-radius: 8px;
padding: 12px;
```

Карточка должна показывать только оперативно значимые данные.

Не превращать Kanban card в уменьшенную форму объекта.

---

# 17. Saved entity pages

Для сохранённых сущностей используется единая архитектура:

1. левый sidebar = глобальные модули;
2. верхние entity tabs = разделы сущности;
3. центральная рабочая область;
4. правая context rail только там, где она реально полезна.

Примеры:

### Заявка

`Обзор | Позиции | Расчёты | КП | Согласование | История`

### Клиент

`Обзор | Контакты | Заявки | Расчёты | КП | Объекты | Документы | Финансы | Журнал действий`

### КП

`Обзор | Документ | Согласование | История`

Side step navigation используется **только в создании / редактировании формы**, а не как постоянная навигация сохранённой сущности.

# 19. Sections / panels

Базовый radius коммерческого baseline:

```css

```

Section header:

```css

```

Основной принцип:

Запрещено дробить каждый key-value на отдельную карточку.

# 20. Drawer

Стандартный коммерческий drawer:

```css
width: min(490px, 100vw);
height: 100dvh;
```

Header / body:

```css
padding: 24px;
```

Drawer используется для:

- быстрого просмотра;
- создания;
- компактного редактирования;
- контекстных действий.

Drawer не должен становиться вторым полноценным приложением внутри приложения.

---

# 21. Responsive

Desktop остаётся основной рабочей средой.

При уменьшении ширины:

- sidebar может переходить в compact/mobile;
- KPI: 4 → 2 → 1/2 по ситуации;
- filter bar переносится;
- detail grid становится одной колонкой;
- таблица получает собственный horizontal scroll;
- context rail может скрываться / становиться drawer;
- не уничтожать данные ради mobile.

---

# 22. Dark theme

Dark theme — отдельная система токенов, а не CSS inversion.

Нужно проверять:

- контраст;
- borders;
- muted text;
- semantic statuses;
- action button;
- таблицы;
- drawer;
- active navigation;
- focus states.
