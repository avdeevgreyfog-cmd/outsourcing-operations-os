# OPERIS · Защита staging-миграций границей БД

Дата: 07.10.2026. База: beta `2ed87ec219184c0636433310b1cd501dd0919f49`.
Рабочая ветка: `fix/guard-staging-migrations-20261007`. PR #79 → `beta`.
Production / `main` кодом этой итерации не изменяются.

## Что обнаружено

- Merge PR #78 в `beta` автоматически запустил `staging-database.yml`.
- `production-database-identity` в отдельном Release Readiness workflow завершился ошибкой: `PRODUCTION_DATABASE_URL` отсутствует в environment `production`.
- Несмотря на это, старый `staging-database.yml` не зависел от Release Readiness и отдельно применил `0066_tender_bid_rounds.sql` к staging DB.
- Откат не выполнялся. Это было бы дополнительным destructive-риском.
- Staging smoke после этого прошёл и подтвердил активный staging commit `2ed87ec...`, `environment=staging`, `schemaVersion=0066_tender_bid_rounds.sql`.
- Тот же staging smoke не упал на проверке production `schemaVersion===0066_tender_bid_rounds.sql`. Следовательно production runtime тоже видит схему `0066`. Без production database identity это не позволяет доказать, что staging и production физически разные.

## Что исправлено

- `.github/workflows/staging-database.yml` теперь сам вычисляет безопасные identities staging и production PostgreSQL до миграции.
- `migrate-staging` имеет обязательную зависимость от успешного `verify-database-boundary`.
- Если production secret отсутствует, identity пустая или identities совпадают, staging migration блокируется.
- `.github/workflows/release-readiness.yml` запускает boundary-check через `always()`, поэтому отсутствие одной identity отображается как явный failure, а не как skipped.
- В `tests/migration-safety.test.mjs` добавлены статические регрессионные тесты на эти зависимости.

## Ограничения

- `PRODUCTION_DATABASE_URL` этим изменением не добавляется и credentials не меняются.
- Физическое разделение staging/production PostgreSQL всё ещё не подтверждено.
- До подтверждения границы БД не выполнять новые staging/production migrations и не выполнять promotion в `main`.

# OPERIS · Тендеры — торги и история цены

Дата: 07.10.2026. База: beta `4a76c372bc4fc2f178c2101ca220ced9ec7b28a7`.
Рабочая ветка: `feat/tender-trading-history-20261007`. PR #78 → `beta`.
Production / `main` этой итерацией не изменяются.

## Что изменено

- Добавлена отдельная append-only история ценовых раундов тендера: первая цена фиксируется при подаче, дальнейшие изменения идут только через вкладку «Торги».
- Существующее `final_bid_value` сохранено как совместимое текущее значение. Миграция `0066_tender_bid_rounds.sql` переносит существующую цену в первый исторический раунд без выдумывания старой маржи или НДС.
- Раунд хранит цену, время, источник, ссылку/протокол, комментарий, автора и server-side snapshot экономики.
- Маржа считается только по одной последней утверждённой версии расчёта тендера. Для каждой позиции нужен принятый сценарий этой же версии, сопоставимый объём и единица тарификации; смешанная тарификация или неполные данные оставляют маржу неизвестной.
- При цене «с НДС» для расчёта net revenue требуется единая известная ставка НДС по всем исходным сценариям. Неизвестный или конфликтующий НДС не подменяется предположением.
- Snapshot себестоимости не возвращается из POST записи торгов. В карточке он показывается только при наличии `calculation.scenario.read` и row-scope ко всем сценариям, вошедшим в snapshot.
- Запись раунда требует `sales.tender.edit`, `sales.tender.submit`, row-scope тендера и этап `submitted` / `awaiting_result`.
- После подачи старый редактор «Подача» больше не может тихо менять цену; отсутствие поля цены в PATCH сохраняет текущее значение, а явное изменение направляется через «Торги».
- Таблица `tender_bid_rounds` защищена tenant RLS, context-integrity trigger, audit и запретом UPDATE; исправление цены оформляется новым раундом.

## Цель и решения

Перенести `/tenders` на общий реестровый контракт заявок и сотрудников. Сохранены серверные карточки, расчёты, согласования, документы, импорт, связи и девять доменных этапов. KPI находятся в аналитике. Виды сохраняют только предпочтения браузера с tenant/member/role/capability scope.

Аналитика различает текущий снимок, когорту создания и календарные события, включая старые тендеры. Только подтверждённые события; нет восстановления пропущенных этапов или синтетической demo-истории. Неизвестные знаменатели дают «—». Суммы — по заполненным текущим бюджетам и потребности, без исторических снимков. Старый trigger не хранит очистку результата: показывается последний записанный результат; ограничение раскрыто в интерфейсе. Миграций и изменений API записи нет.

Демо-записи создания/импорта живут только в памяти до reload и не включаются в аналитику. Демо-reаd scope наследуется от коммерческих заявок, одинаков для реестра, подробной карточки и аналитики. В рабочей системе доступ продолжает загружаться из БД. Общий `SalesDrawer` получил только необязательный overline с прежним значением по умолчанию.
