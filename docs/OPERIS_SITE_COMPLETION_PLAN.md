# OPERIS — план общей доработки и передачи работы

Версия 1.0 · 11.10.2026, Москва.
Статус: продуктовые решения собраны; общий аудит и реализация этапов ниже ещё не выполнены.
Основание: ответы пользователя в текущем чате, 18 вопросов в шести карточках по три вопроса.

## 1. Назначение документа и приоритет источников

Документ позволяет продолжить работу в новом чате без повторного опроса пользователя.
Он уточняет прежние проектные документы, но не подтверждает наличие описанных функций в коде.

Приоритет: последние явные решения пользователя → данный датированный план в части новых решений → актуальные контракты UI и редактирования → исходные Foundation / Visual Language / Development Rules / Target Navigation / Architecture and Roadmap / Visual Baseline.

При конфликте не переписывать прошлую историю молча: записать решение, основание и затронутые процессы. Код является доказательством реализации, а не автоматическим согласованием поведения.

## 2. Цель и границы

Довести существующий OPERIS до согласованного визуального и рабочего поведения по всему сайту. Пользователю не требуется отдельно проверять каждую страницу. Основной разработчик проверяет результат и показывает законченные блоки в Preview.

Различать три вида работ:
- исправление ошибок существующей реализации;
- унификация оформления и действий;
- развитие функций, согласованных ниже, но пока отсутствующих или частично реализованных.

Не обещать отсутствие всех ошибок. Для каждого выпуска указывать фактическое покрытие проверки и оставшиеся ограничения.

Сохранять существующий репозиторий, серверные данные, ID, связи, историю, capability-based доступ и утверждённые версии. Не заменять приложение статическим макетом или браузерным хранилищем. Бухгалтерский и налоговый учёт остаются во внешней системе, например 1С.

## 3. Согласованная структура продукта

Названия ниже — рабочая основа. Окончательные понятные подписи уточняются в ходе аудита; самостоятельные процессы не исчезают ради сокращения меню.

| Раздел | Назначение | Основной состав |
| --- | --- | --- |
| Рабочий стол | Личная работа сотрудника | Задачи, сроки, согласования, блокеры и доступные показатели по должности; командные задачи для руководителей |
| Коммерция | Получение и согласование заказа | Клиенты, заявки, тендеры, расчёты, КП, согласования, договоры |
| Подбор и персонал | Закрытие потребностей и история людей | Потребности, распределение, воронка, кандидаты, подготовка, сотрудники |
| Операции | Запуск и ведение объектов | Объекты, запуск, комплектация, назначения, смены, табели, инциденты |
| Обеспечение | Заявки и ресурсы | Заявки, закупки, склады и СИЗ, жильё, транспорт, поставщики, связанные документы |
| Финансы и аналитика | Управленческая экономика | Экономика объектов и компании, план/факт, расходы, начисления, оплаты, вознаграждения, доступные аналитические представления |
| Компания | Ответственность и структура | Дерево компании, сотрудники офиса, должности, подразделения, обязанности, руководители и ответственные |
| Настройки | Работа приложения | Модули, права, справочники, шаблоны, процессы и технические настройки |

Самостоятельный верхний раздел «Контроль» не требуется. Его полезные функции распределяются: история в карточках и общем журнале, документы и сроки в соответствующих рабочих очередях, технический аудит в Настройках. Сначала составить карту переноса функций и ссылок; затем менять навигацию. Скрытие пункта не означает удаление данных или API.

Объединение Финансов и Аналитики — единый вход, не уничтожение специализированных представлений. Аналитика подбора и операций доступна из соответствующего рабочего контекста; финансовые данные остаются защищены правами.

## 4. Заказ, самостоятельный вход и параллельные процессы

Типовая цепочка: обращение / заявка / тендер → расчёт → КП и согласование с заказчиком → согласованный заказ → договор, подбор и подготовка объекта → работа → табель → начисления / расходы / оплаты → экономика.

Заявка создаётся менеджером, в том числе по телефону, либо заказчиком через существующую публичную форму. Если цена не подходит, создаётся корректировка / новая версия расчёта и предложения; цикл повторяется до согласия или отказа. Принятые версии не перезаписываются.

Передача в подбор обычно после согласования цены, по явному действию уполномоченного сотрудника. Руководитель может разрешить предварительный старт с фиксацией решения. Договор может подписываться параллельно и не блокирует автоматически начало рекламы и подготовки.

На каждом рабочем участке разрешён самостоятельный вход:
- создать потребность в подборе без коммерческой заявки;
- создать действующий объект без прохождения коммерческой цепочки;
- загрузить существующие объекты, людей и исходные данные;
- продолжить нужный процесс, если предыдущие этапы проходили вне приложения.

Отсутствующая связь отображается честно. Не создавать фиктивные заявки, расчёты или договоры, чтобы удовлетворить технический маршрут. При самостоятельном создании всё равно проверять обязательные для самой сущности поля, права и принадлежность организации.

Открытые существенные решения для точечного согласования по итогам аудита: условия разрешения первого фактического выхода без договора; полномочия на исключения; состав начальных данных и дата начала финансового учёта при импорте действующего объекта. Эти детали не считать уже утверждёнными.

## 5. Уточнения менеджера объекта

После посещения объекта менеджер дополняет данные для запуска и подбора. Например, обнаруженная потребность в проживании может изменить расходы.

Нефинансовые уточнения сохраняются с историей в рамках прав. Изменения, влияющие на стоимость, фиксируются как предложение ответственному руководителю. Руководитель выбирает:
1. Пересчитать и повторно согласовать условия с заказчиком.
2. Сохранить согласованную клиентскую цену и принять дополнительные внутренние затраты.

Решение, основание, новая оценка затрат и влияние на маржу должны быть видны. До решения не подменять утверждённые условия незаметно. Изменения численности, графика, ставок и обеспечения оценивать по влиянию на экономику, а не только по названию поля.

## 6. Подбор, подготовка и человек

Руководитель распределяет общую потребность по подборщикам с количеством людей, сроком и ответственностью. Суммарные задания и фактическое закрытие не должны создавать двойной учёт одной потребности.

Процессы основаны на шаблонах с настройкой для объекта. Например, проверка СБ, медицина и медкнижка могут быть обязательны на одном объекте и не использоваться на другом. Компания выбирает применимые шаги, документы, ответственных и сроки; может дополнять настройки. Неиспользуемые шаги не выдаются за выполненные.

Сначала доработать существующую структуру кандидатов и сотрудников. Общие данные и документы передаются без повторного ввода. Сохранить историю подбора, выходов, назначений и завершения работы. Увольнение не удаляет человека. Повторный приход связывается с прежними данными и новым эпизодом работы; история предыдущего периода остаётся доступна по правам.

Не создавать отдельную кадровую бухгалтерию. Нужны шаблоны заявлений, список требуемых документов, собранные файлы и история подготовки. Эти данные видны в карточке человека и связанных процессах.

Масштаб автоматической дедупликации и правила объединения найденных совпадений уточнять по существующей модели. Не объединять людей только по одинаковому ФИО.

## 7. Обеспечение

Один модуль для заявок сотрудников и ресурсов. Сотрудник создаёт запрос в контексте объекта или потребности; ответственный обрабатывает его, согласует, закупает / перемещает, фиксирует получение и выдачу.

Различать офисный / центральный склад и склады объектов. Назначать ответственных; учитывать перемещения, выдачу, возврат и остатки. Не дублировать один и тот же предмет на нескольких складах без движения.

Жильё, транспорт, поставщики и их расходы связываются с объектом и людьми там, где связь существует. Документы и кадровая подготовка остаются в соответствующих карточках; шаблоны доступны централизованно.

Детали оценки запасов, частичной выдачи и распределения общей закупки между объектами проверять по реализации и согласовывать, если меняются финансовые правила.

## 8. Финансы, аналитика и вознаграждения

Это управленческий контроль: сколько объект приносит, сколько расходует, где отклонения и какой итог по компании. Не реализовывать бухгалтерские проводки, налоги и регламентированное закрытие периода.

Источники факта: рабочие данные приложения, ручной ввод подтверждённых расходов / оплат и импорт. Для данных фиксировать источник, период, объект, состояние подтверждения. Не учитывать дважды один расход из закупки и повторного ручного ввода.

Различать план, начислено, фактически оплачено и подтверждённый объём заказчика. Денежный поток и прибыль — разные показатели. Не объявлять полученную оплату выручкой повторно поверх уже признанного объёма услуг.

Компания выбирает, какие контуры финансов ведёт. Основной приоритет — прямые расходы и доходы объектов; офисные и общие расходы возможны, но их отсутствие не блокирует работу.

Показывать полноту исходных данных и границы результата: если часть расходов не внесена, не выдавать промежуточный вклад объекта за окончательную чистую прибыль компании. Неизвестные значения отображать как неизвестные, а не нули.

Оплата заказчиком: часы / смены, объём, фиксированная стоимость. Отдельный рекрутинг за вознаграждение не включён в ближайший согласованный объём.

Вознаграждения менеджеров и подборщиков: настраиваемые схемы — фикс, процент, оплата за человека / событие / отработанный период. Версионировать по датам действия. Расчёт по событиям системы → проверка ответственным → утверждение. Исторические начисления не пересчитываются по новой схеме молча.

До внедрения сложных схем уточнить конкретные формулы, базу процента, распределение между объектами и трактовку отработанного периода. Пользователь разрешил настраиваемые схемы, но не утвердил каждую формулу.

## 9. Рабочий стол, компания и права

Рабочий стол — шаблон по должности с настройкой: добавление доступных блоков, скрытие, перемещение и настройка. Обязательные рабочие действия должны оставаться достижимы независимо от персональной раскладки. Скрытие блока не отменяет задачу, уведомление или ответственность.

Руководитель видит командные задачи, исполнителей, сроки, просрочки и результаты. Использовать единый механизм задач; не создавать новую систему задач внутри каждого модуля.

Дерево компании показывает, кто кому подчиняется и по каким вопросам отвечает. Есть один непосредственный руководитель и отдельные ответственные по объектам / процессам. Эти связи не подменяют друг друга. При нескольких объектах полномочия определяются реальным назначением.

Права: стандарт по должности + область ответственности + индивидуальные разрешения / запреты. Новому сотруднику назначается должность и scope; права можно уточнить. Сохранять различие должности, процессной роли и capability. Финансовые и личные данные проверять на сервере; скрытая кнопка не является защитой.

Уведомления в этой доработке — внутри приложения: рабочий стол и общий центр уведомлений. Мессенджеры и email — отдельный будущий этап. Не отправлять внешние сообщения автоматически.

## 10. Общий UI и редактирование

Использовать `docs/OPERIS_UI_STANDARD.md`, `docs/SALES_EDITING_CONTRACT.md`, актуальный Visual Baseline и общие компоненты. Сохранять Segoe UI с кириллицей, спокойные поверхности, небольшие радиусы, информационную плотность, оранжевый акцент действий и статусы с точкой / подписью без ярких плашек.

Общие сценарии там, где они подходят:
- название записи / глаз → быстрый просмотр;
- явное действие → предзаполненное быстрое редактирование;
- стрелка / «Открыть карточку» → полноценная карточка;
- в карточке → редактирование выбранного блока;
- добавление небольших связанных данных → общая встроенная форма;
- создание основной сущности → отдельный полноценный сценарий;
- сохранение / отмена, ошибки с сохранением ввода, предупреждение о несохранённых данных.

Табели, расписания, расчёты и документы сохраняют нужные им специализированные рабочие области. Общий стиль не требует одинакового размера всех панелей или состава форм.

Проверять понятные русские подписи, длинные названия, центрирование текста в кнопках и счётчиках, отступы от границ, единые высоты контролов, компактность строк, клавиатуру и обе темы. Дополнительные данные раскрываются, а не удаляются.

| 1. Полный аудит | Все пункты навигации, вложенные вкладки, реестры, карточки, создание, редакторы, очереди и роли | Реестр экранов с проблемами, приоритетом, зависимостями и фактическим статусом проверки |

| 7. Финансы и аналитика | Единый вход, источники факта, экономика, полнота данных, схемы вознаграждений | Формулы и источники проверены; факт и план не смешиваются; доступ соответствует роли |
| 8. Рабочий стол и компания | Шаблоны и персональные настройки, командные задачи, дерево, должность и scope, уведомления | Рабочая информация соответствует роли; пользователь не получает лишних полномочий |
| 9. Навигация и настройки | Убрать доказанные дубли, распределить Контроль, согласовать новые названия | Все прежние полезные действия достижимы; ссылки сохранены или корректно перенаправляются |
| 10. Сквозной выпуск | Проверить межмодульные сценарии, роль / tenant / scope, регрессии и Preview | Ссылка ведёт на проверенный commit; отчёт содержит реальное покрытие и ограничения |

Этапы 3–9 могут иметь независимые подзадачи, но источники данных, права и версии проверяются до расширения интерфейса. Сначала исправлять потерю данных, ошибки прав, сохранения и расчётов; затем неработающие действия; затем визуальные расхождения и удобство.

Аудит отделяет развитие отсутствующей функции от дефекта. Не превращать незавершённый пункт в декоративную страницу с фиктивными данными. Новые функции реализовывать законченно по выбранному приоритету.

## 12. Рабочий реестр и доказательства

Создать `docs/OPERIS_SITE_AUDIT.md` после проверки актуального кода. Для каждой строки записывать:

`ID | маршрут / вкладка | роль | сценарий | проблема | приоритет | исправление | зависимость | статус | commit | проверка | Preview`.

Статусы: не проверено → проверено / проблема найдена → в работе → исправлено → проверено локально → проверено на Preview. Состояние «нужно решение» отдельно. Публикация не означает проверку, просмотр страницы не означает проверку сохранения.

Сохранять в репозитории краткий `docs/OPERIS_SITE_HANDOFF.md`: актуальные SHA main / beta / рабочей ветки, выполненные этапы, незавершённые задачи, решения пользователя, файлы подзадач, команды QA, ссылки на CI / Preview и конкретные блокеры. Обновлять после каждого законченного блока и перед переходом в новый чат.

## 13. Минимальная проверка выпуска

Для затронутых процессов проверять:

TypeScript, lint, build, релевантные unit / integration и браузерные проверки фиксировать на конкретном SHA. Ключевые сквозные сценарии: заявка → пересчёт / согласование → подбор + подготовка + договор; самостоятельный действующий объект → потребность → человек → смена → табель; уточнение проживания → решение руководителя → затраты; заявка обеспечения → движение ресурса → расход; увольнение → повторный приход; начисления / оплаты / расходы → итог экономики с обозначением полноты.

## 15. Субагенты и экономия

Пользователь явно разрешил применять субагентов там, где это полезно, и более лёгкие модели для ограниченных задач без ухудшения результата.

Лёгкая модель подходит для инвентаризации маршрутов, поиска технических подписей, проверки согласованных размеров, обновления документации и простых локальных правок. Не уменьшать модель только ради экономии. Если растёт число исправлений или проверок, использовать основную. Передавать короткий контекст: цель, контракт, файлы, запреты, критерии и формат результата. Не копировать весь чат всем агентам. После делегирования читать изменения и проверять их в интеграции; ответ агента сам по себе не доказательство.

Конкретные доступные модели и число агентов проверять в текущей среде. Название пользовательской модели не гарантирует доступность такого же выбора в инструменте.
