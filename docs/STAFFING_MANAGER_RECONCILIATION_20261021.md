## Инварианты

- Источник истины по численности: `staffing_plan_targets`. Источник истины по условиям: `object_specialty_conditions`. Потребности остаются в `needs`.
- Ставки/смены/периоды/индивидуальные исключения не переносились в `needs` или глобальный справочник специальностей; старые снимки факта и табеля не затрагиваются.
- Создание или увеличение потребности никогда не увеличивает план автоматически.
- Для увеличения потребности блокируется строка плана, затем потребность; сумма запрошенного объёма проверяется относительно фактически работающих и действующего подбора.
- Старые потребности без `staffing_plan_target_id` не соединяются автоматически по текстовым названиям: UI предупреждает и блокирует рискованное создание дубликата, пока связь не разрешена вручную.
- Права на редактирование проверяются в обработчиках, а не только кнопками.

## Ограничения и дальнейшая приёмка

1. Нет подтверждённого нового HTTP write-E2E именно новых операций, под тестовыми ролями и native PostgreSQL. Прохождение общих PostgreSQL/HTTP suite — регрессия соседних контуров, не доказательство нового сценария.
2. Глобальные прогнозные показатели и точная комплектация по строке специальность/смена вычисляются разными представлениями; необходима дополнительная сверка многосменных объектов.
3. Периодная версия **плана численности** пока хранится как изменение текущей строки плюс `activity_events`; полноценную неизменяемую временную версию строк плана не добавляли. Версии **условий оплаты** не изменены.
4. Старые несвязанные потребности требуют безопасной миграции/ручного сопоставления ID; автоматического соединения по специальности и объекту не делали.
5. Нужна фактическая браузерная проверка объекта и глобального плана (desktop/mobile, обе темы), а также проверка отказа в записи для ограниченных ролей.
6. Сливать в `pilot` и `main` и переключать Vercel alias только после этой приёмки и проверки схемы/staging.
