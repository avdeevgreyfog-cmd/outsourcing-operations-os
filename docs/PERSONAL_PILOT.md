## Причина прежней проблемы входа

Старый production `/api/system/status` показывал SHA `36c5129`, databaseIdentity
`a361acd783643cdd`, schema `0073`. Этот fingerprint совпал с pooled endpoint
ветки `br-little-bread-b7f9cor7` проекта с названием staging. У личного владельца
в этой базе password_hash был NULL; браузерный вход вернул «Неверная почта или пароль».

В исходном проекте `wandering-shadow-57829895` аккаунт владельца активен и имеет
сохранённый bcrypt-хеш. Он восстановлен только в отдельном пилоте для того же
пользователя и организации. Пароль не включался в исходники или этот отчёт,
не сбрасывался в оригинальной базе и не менялся в старом production/staging.
Старая production-конфигурация остаётся отдельной инфраструктурной задачей;
личные данные нужно вводить через адрес пилота.

## Чистый рабочий контур

На старте в личной организации нет объектов, сотрудников, кандидатов, клиентов,
потребностей, табелей и других операционных записей. Сохранены владелец,
его должность/членство, роли/права, структура и системные справочники, необходимые
для начала работы. Старые security audit события не стирались ради внешней чистоты.
Данные исходного проекта и других организаций не очищались.

## Дополнительное исправление записи

Ряд существующих сервисов использует `sql.begin` внутри уже открытого withTenant.
postgres.js предоставляет в такой транзакции `savepoint`, а не новый `begin`.
Из-за этого ручное добавление сотрудника и другие такие записи могли падать.
Общий tenant client теперь выполняет вложенные begin через savepoints на том же
соединении. Они сохраняют tenant/user/role и не могут выйти из внешнего rollback.
Опции, меняющие изоляцию вложенной транзакции, явно запрещены.

Проверены build/TypeScript, 398 тестов, targeted lint, native PostgreSQL:
ручное создание сотрудника с назначением, сохранение, вложенный/внешний rollback,
NOSUPERUSER/NOBYPASSRLS и одновременные tenant contexts. Повторён весь native
сценарий кабинета/плана/часов/блокировки/увольнения. Остальные операции приложения
не объявляются полностью проверенными лишь на основании общей правки.

Проверка действующего пароля в новом браузерном входе должна подтверждаться
появлением владельца и рабочей организации на странице; перенос хеша сам по себе
не считается успешным входом.
